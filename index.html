Key distinction

A wallet can be an interface or credential store. A tokenized card transaction in a supported wallet generally uses the underlying card rails rather than becoming a new payment rail.

Key operating principle

An unknown or timed-out status is not proof of failure. Query and reconcile the transaction before retrying to reduce duplicate-charge risk.

Research scope

High-level public-source learning guide—not integration, legal, compliance or certification advice. Validate exact flow and rules with the relevant participant.

3 · Failure handling playbook

Timeout or final status unknown

Action: query the status API/dashboard, check webhook events and reconcile using payment ID + order ID. Keep the order pending until authoritative status is known.

Avoid: immediately creating a fresh charge after a timeout.

Capture: request/response timestamps, payment ID, order ID, idempotency key, event ID and response-code category.

UPI debit but beneficiary/merchant credit not confirmed

Action: verify current status and bank reference; follow the current applicable NPCI/RBI handling for the specific transaction category and escalate if needed.

Avoid: assuming debit alone confirms the merchant order was paid, or promising one generic timeline.

Payment succeeded but merchant order is unpaid

Action: reconcile order/payment IDs and provider events; repair order state only after status confirmation and process duplicate events idempotently.

Avoid: relying solely on a browser redirect.

Refund initiated but not yet credited

Action: capture refund ID and timestamp, check provider status and applicable issuer/provider guidance, and explain that initiation and statement posting are distinct.

Avoid: promising instant credit for every rail/provider.

Wallet token provisioning/device error

Action: check issuer/card/region/device eligibility and non-sensitive error details; escalate to the proper wallet/issuer/provider support path.

Avoid: requesting or storing full card number, CVV, OTP or UPI PIN in a support ticket.

Refund, reversal and chargeback: what differs?

Authorization reversal/void: release or reverse a supported authorization/hold. Refund: return funds after a completed/captured transaction. UPI failed-transaction reversal: bank/scheme process for specified failure cases. Chargeback/dispute: a separate formal dispute process with its own evidence and deadlines.

4 · Operational tracker and KPI suggestions

Authorization success rateDefine approvals / eligible attempts and segment by response code.
Unknown-status agingCount and age transactions awaiting a definitive state.
Reversal agingTrack applicable failed cases from initiation to confirmed reversal.
Refund turnaroundSeparate provider status from issuer/customer posting where possible.
Reconciliation breaksMeasure unmatched transactions, captures, settlement and payouts.
Partner response SLARecord first response, resolution time and escalation owner.

Minimum case fields: order ID, payment ID, rail, provider, amount/currency, timestamp/timezone, status, response code, idempotency key, relevant bank/provider reference, event timestamps, owner, escalation date and final resolution. Never include authentication secrets.
